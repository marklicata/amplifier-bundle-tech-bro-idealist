# MADE Team Strategy

This document is the authoritative reference for the MADE team's vision, mission, and strategic context.
Load this when evaluating, reviewing, or planning work for the MADE team.

---

## Vision

Use software to get as much leverage out of the models as possible.

---

## Mission

1. Build the platform, tools, patterns, and meta-cognition that produce greater outputs than attention-restricted humans would have otherwise been able to deliver.
2. Prove agentic development changes what a small team can deliver via a software factory where finished products ship as easily as prototypes start.

---

## How We Measure Success

**Every project MADE ships must move at least one of these four AI-native product output metrics:**

| Metric | What It Measures |
|--------|-----------------|
| **Speed** | How much faster work gets done |
| **Ease** | How much friction is removed for developers or users |
| **Quality** | How much better the output is |
| **Cost** | How much cheaper delivery becomes |

These are causal to revenue and user growth — which MADE cannot directly impact because **MADE does not own a product**. If a project cannot name the metric it improves, it does not make the roadmap.

---

## Core Theses

Four theses, mapped to MADE's functional themes (capability, factory, distribution) and laddered to the Vision.

### Thesis 1: One Agent, Any Harness
*Metrics: Speed, Ease*

The durable unit of value is an agent that works across every surface — not a CLI or a single app.

### Thesis 2: Human Attention Is Limited
*Metrics: Quality, Cost, Speed*

Long-running, server-side autonomy that takes complex work from "started" to "done" without a human babysitting it.

### Thesis 3: A New Operating Model for Teams
*Metrics: Ease, Speed, Cost*

When everyone's attention is fully saturated on complicated problems (Thesis 2), the software factory makes finishing products as easy as starting them. The shared platform, data, and patterns allow the team to exploit and accelerate agentic code at scale.

### Thesis 4: Impact, in the Open
*Metrics: Ease, Quality*

A surface that gets MADE's work into real users' hands and proves value — internal adoption and external ROI — not demos in a repo.

---

## Proof We Already Have

Nexus and Scout were built independently, by different teams, on different architectures — and landed on the same user needs. That is external validation the thesis is right, at a scale OCTO doesn't have.

---

## Operating Principles

- **Research doesn't stop** — it becomes the front of a pipeline that ends in shipped product against a roadmap and dates. A research function feeds a delivery/operations function that turns durable ideas into shipped products.
- **Single-threaded ownership** — each thesis has one owner who is accountable for defining what delivery looks like and executing.
- **Output metrics are essential** — every project is tested against the four output metrics. Some current work may not survive that test; the strongest agent bets do.
- **User needs are required** — understanding what human users need of agentic systems is more important than any technology or idea the team may have.

---

## Applying This Context

When evaluating or planning work for MADE, ask:

1. **Which thesis does this advance?** (Theses 1–4, or none — if none, it needs justification)
2. **Which output metric does it move?** (Speed / Ease / Quality / Cost — must name at least one)
3. **What is the impact path?** MADE doesn't own a product, so work needs a named route from repo to real user hands. "We'll demo it" is not an impact path.
4. **Is user need validated?** The team's enthusiasm for a technology does not substitute for evidence that users need it.
